# 微信 4.1.12.51 高效通道验证结论

> 本文档记录 2026-08 在小漓项目中对新版微信（4.1.12.51）自动化通道的实测结论，
> 作为 `wx_backend` 技术路线选型的依据。所有结论均附实测命令与输出。

## 结论速览

| 假设 | 判定 | 证据 |
|---|---|---|
| H1：注入 `--force-renderer-accessibility` 后 UIA 树恢复 | **失败** | `cdp_probe.py inject --args="--force-renderer-accessibility"` 后 check：business_controls=0，仍空壳 |
| H2：注入 `--remote-debugging-port=9222` 后 CDP 可用 | **失败** | 参数确实进入主进程命令行（PID 26384），但无 DevToolsActivePort、9222 无监听、`/json/version` 拒绝连接 |
| H3：重启微信后登录态保留 | **通过** | 3 次 inject/restore 均 `login_ok=true`（主进程+4 子进程就绪） |
| H4：CDP DOM 中聊天列表/消息/输入框可定位 | **不可测** | H2 失败，无 CDP 通道可连 |
| 附加：微信进程监听端口（隐藏 CDP） | **不存在** | netstat 全部微信 PID 无 LISTENING |
| 附加：窗口消息模拟（WM_SETTEXT/子窗口） | **不可行** | EnumChildWindows 主窗口零子窗口——内容全在 Chromium 渲染层 |
| 附加：本地消息数据（radium\web\profiles / login\wxid） | **不可读** | profiles 仅 game/webview/multitab 内嵌 web profile；login\wxid 仅 key_info.dat（加密凭证）；消息存储为加密 mmkv |

## 关键判定证据

### H1：accessibility 强制开启（失败）

```bash
.venv/Scripts/python.exe tools/cdp_probe.py --timeout 120 inject --args="--force-renderer-accessibility"
```

输出关键行：

```
启动: 'D:\腾讯\Weixin\Weixin.exe' '--force-renderer-accessibility'
[OK] 微信已就绪(进入主界面)   ← 5 进程，登录态保留
[OK] 主窗口: class='Qt51514QWindowIcon' name='微信'
[FAIL] 子树为空壳(仅 Pane), accessibility 未开启或未桥接
"business_controls": 0
```

**结论**：`--force-renderer-accessibility` 是标准 Chromium 参数，但微信的 Chromium 是深度定制的（wxocr/wxutility 等自有 type），参数未触发 UIA 桥接。

### H2：CDP 远程调试（失败）

```bash
.venv/Scripts/python.exe tools/cdp_probe.py --timeout 120 inject --args="--remote-debugging-port=9222"
```

输出关键行：

```
[OK] 微信已就绪(进入主界面)   ← 登录态保留
[FAIL] DevToolsActivePort 不存在: ...\radium\web\DevToolsActivePort
[FAIL] /json/version 不可达: WinError 10061 连接被拒绝
[FAIL] /json 不可达: 同上
```

进程命令行复核（PowerShell `Get-CimInstance Win32_Process`）：

```
ProcessId : 26384
CommandLine : D:\腾讯\Weixin\Weixin.exe --remote-debugging-port=9222   ← 参数确实传入
```

端口复核：

```
netstat -ano | grep LISTENING | grep -E ":(26384|...)$"   → 无结果
curl http://127.0.0.1:9222/json/version                    → 不可达
```

**结论**：参数传入但微信的 Chromium 未启动调试服务——CDP 被微信侧禁用/剥除。`DevToolsActivePort` 在 `radium\web`（其 Chromium user-data-dir）下未生成。

### H3：登录态保留（通过）

3 次注入/还原操作（force-renderer-accessibility → remote-debugging-port → 无参数）均观察到：

```
Weixin.exe 进程数: 1 → 5
[OK] 微信已就绪(进入主界面)
"login_ok": true
```

**结论**：微信 4.1.12.51 重启后自动登录（登录态存于 `xwechat\login\wxid_*\key_info.dat`），注入参数实验不会破坏登录态。

### 附加：窗口消息模拟（不可行）

```python
EnumChildWindows(主窗口 hwnd) → 子窗口数: 0
```

**结论**：主窗口 `Qt51514QWindowIcon` 无任何 Win32 子窗口——全部 UI 内容在 Chromium 渲染进程内（同 UIA 空壳的解释一致）。WM_SETTEXT/按键模拟无目标控件可发。

### 附加：瞬态 UIA 树（不可复现，已排除）

首次注入 `--remote-debugging-port` 后 check 曾报告 `class='mmui::MainWindow'` + 15 个业务控件（GroupControl/ToolBar 导航/ButtonControl 置顶）。复现实验（同参数再注入 + 60 秒持续采样）均回到 `Qt51514QWindowIcon` + 0 控件。

**结论**：这是微信启动早期（登录完成瞬间、Chromium 渲染接管前）的原生窗口窗口期，且仅含导航/置顶等外壳控件、无聊天列表/消息控件——不可作为稳定通道。

## 技术路线锁定

**所有"高效通道"（UIA / CDP / 窗口消息 / 本地数据）在新版微信 4.1.12.51 上全部关闭。**
唯一可用通道是 **PrintWindow 截图 + 视觉识别**（`wxauto_new_feasibility.md` 5.1 已验证）。

对 `wx_backend` 实现的直接影响：

1. **visual_backend 从"保底降级"升级为主后端**——不是备胎，是唯一实现。
2. **效率优化方向从"换通道"转为"降识别成本"**——用户的效率诉求（"不想要每次轮询多模态 AI"）通过以下手段满足：
   - **变化检测先行**：PrintWindow 截图后先做本地像素差异检测（毫秒级），无变化直接跳过——避免每轮调视觉 API。
   - **OCR 替代多模态**：文本消息用本地 OCR（Windows OCR API / Tesseract / 微信自带 WeChatOcr 插件的 wxocr.dll）提取文本，只有图片消息才调多模态 AI 描述。视觉 API 只在"真新消息"时调用。
   - **事件驱动语义**：轮询周期内"变化→识别→处理"，等效于 wxauto4 的"新消息→处理"。
3. **架构解耦仍然成立**：`wx_backend` Protocol + 注册表 + auto 降级照计划实现；visual_backend 是第一个（也是当前唯一）注册实现；未来若微信暴露新通道（如官方适配、CDP 复活），注册新后端即可热切换。
4. **UI 定位器与业务逻辑解耦原则不变**：视觉坐标定位集中在 visual_backend 内部，`wechat_bot.py` 上层业务无感知。
