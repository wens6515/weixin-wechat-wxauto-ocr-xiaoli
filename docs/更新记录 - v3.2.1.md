# 更新记录 · v3.2.1「初始化失败诊断与显示缩放前置」

## 初始化失败诊断弹窗

此前初始化失败只有一条 3.6 秒的 toast 和首页状态行的一行小字——失败原因（微信没开 / 截图失败）和「接下来该做什么」全靠用户自己从日志里猜。本版失败必弹诊断弹窗：

- **失败原因**（红字原文）+ **当前检测**（显示缩放百分比值、微信窗口是否找到——现场即时值，用户改完设置不用重启就能在弹窗里看到变化）；
- **修复指引**按错误类型生成：微信未找到 → 打开并登录电脑版微信后重试；缩放不符 → 给出完整设置路径；截图失败 → 恢复微信窗口显示/重启微信与小漓；
- 弹窗内直接点**「重试初始化」**，修好环境一步到位；
- 运行中的瞬态主循环异常仍只走 toast（不弹窗打扰），弹窗只属于「初始化失败」这个需要用户动手的情景。

## 显示缩放 175% 成为连接硬前置

小漓的全部像素判据（头像窄带、头像高 63px、气泡与媒体闸、文件卡片图标）都按 **175% 缩放**下的 1300×1610 窗口逐像素标定——缩放不符时此前的行为是「窗口照常连上、消息却读错甚至一条都读不到」的**隐性故障**，用户全程看不到任何报错。本版在连接微信时做缩放预检：

- 非 175% → **立即失败**（不进 30 次重试循环），错误消息带实际缩放值与设置路径，由上面的诊断弹窗承接；
- 检测不出缩放（返回未知）不拦截——检测手段失效不该把人挡在门外；
- CLI 模式同样立即失败并给出原因，不再无限重试。

## 缩放检测改为实时值（不重启也能读对）

真机实测暴露的问题：以 125% 启动小漓、随后把系统缩放改到 175%，程序仍一直读到 125%（重检、初始化都判错），必须重启才恢复。根因是**进程级** DPI 声明在 GUI 进程里会因窗口已创建而失败，进程被系统做 DPI 虚拟化——`GetDpiForMonitor` 只会返回进程启动那一刻的值。本版把 DPI 查询放进 **per-monitor v2 线程上下文**里执行（查询期间切换线程上下文、结束恢复）：DPI API 按调用线程的感知级别作答，改完缩放**不用重启**即可读到显示器当前真实值；旧系统拿不到该 API 时退回原行为（重启兜底）。

## 首页环境检查：显示缩放卡 + 指示灯修复

- 新增「显示缩放」检测卡：175% ✓ 绿灯；非 175% **红灯**并给出设置路径（此前检测失败指示灯只是不亮——灰色与失败无法区分，红灯样式本版补齐）；检测不出为中性灰。启动时缩放不符还会 toast 明说，不必等到初始化失败。
- 环境卡布局改为**永远单行横排、等分占满**（此前四张卡在窄窗口会折成上下两列）；卡数随任务桥开关浮动——任务桥关闭时「天枢 CLI」「首轮提示词」两张卡隐藏（它们只服务任务桥），首页恒定是「微信 PC 版 + 显示缩放」或四张全开，总占位不变。
